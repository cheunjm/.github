# .github

Default GitHub templates and reusable workflows for all `cheunjm` repos.

## What belongs here

- Issue templates (bug, feature, chore)
- PR template
- Reusable GitHub Actions workflows (Claude Code, code review, changelog, etc.)
- GitHub-specific configs (FUNDING.yml, CODEOWNERS, etc.)
- Tools registry (TOOLS.md)

## What does NOT belong here

- Coding conventions, standards, or style guides → `cheunjm/conventions`
- Repo-specific workflows or configs → the repo itself
- Secrets, credentials, or environment values → 1Password

## When to update this repo

When working on any `cheunjm` repo and you notice:
- A GitHub workflow being duplicated across repos — extract it here as a reusable workflow
- An issue or PR template improvement that should apply everywhere
- A new GitHub App or tool installed — update TOOLS.md

Ask Jace before adding or changing defaults — these affect all repos.

## Verification

After implementing changes, always run the test/verification steps from the plan before committing or opening a PR. After merging, verify the changes work on the default branch when possible. This includes running workflows locally (e.g. `act`), validating YAML syntax, and testing that calling repos can reference updated workflows. Do not treat verification as optional or skip it.

Other repos call these via `uses: cheunjm/.github/.github/workflows/{name}.yml@main`. Available:

The logic is `scripts/contract_check.py`, fetched from `cheunjm/.github` at `scripts_ref` (default `v1`) so a caller needs the release that carries it. Tests: `python3 -m unittest scripts/test_contract_check.py`. |
| `auto-update-branches.yml` | Push to default branch (merges it into open non-draft same-repo PRs that target it; never rebases) |
| `notify-merge.yml` | Push to default branch (parameterized: `slack_channel`, `repo_label`) |
| `changeset-check.yml` | Pull request (caller workflow is named `Release notes` with job id `changeset`, so GitHub shows `Release notes / changeset / check`): fails unless the PR adds a new `.changeset/*.md` (empty allowed), diffed against the PR's own base so each stack layer needs its own; validates with the pinned changesets CLI; `changeset-release/*` and `dependabot/*` are exempt. Same `scripts_ref` as above. |
| `changeset-version.yml` | Push to default branch + `workflow_dispatch`: keeps one "Version Packages" PR per repo using the `arami-bot` token; optional `publish`, `install-command`, `registry-url`, `scope` inputs and `PKG_READ_TOKEN` secret. Pins `@changesets/cli` and `changelog-github` and installs them ephemerally (`--no-save`), so repos carry no changesets dependency. Repos that already declare both packages and install them (monorepos, private registries) pass `install-tooling: false` and use their own versions. Runs `changesets/action` v2, which refuses to run on Changesets CLI v2: keep the CLI on 3.x (Node 22+) here and in any repo that declares its own. Its v1 inputs were renamed (`version-script`, `publish-script`, `pr-title`, `commit-message`), and it needs the token via `github-token`. `tag: true` (when `publish` is empty) runs `changeset git-tag` once the Version PR merges, which creates and pushes `vX.Y.Z` and a GitHub release; an existing tag is skipped, so later pushes are no-ops `app-json` (default empty, INF-1983 D44): after `changeset version`, sets `.expo.version` in that file to the new `package.json` version in the same Version PR commit (2-space JSON, trailing newline kept; fails with `<file> has no expo.version to set` when missing), via `scripts/sync_app_json.py` at `scripts-ref` (default `v1`). Tests: `python3 -m unittest scripts/test_sync_app_json.py`. |
| `changeset-prerelease.yml` | `workflow_dispatch` via caller (`phase`: `enter-dev` / `enter-rc` / `release-stable`): opens a PR that enters or exits changesets pre mode instead of pushing to the default branch |
| `ci.yml` | `workflow_call`, stack-agnostic CI in **one job** (INF-1983 D5, D34, D35): with caller job id `ci` the only check is `ci / gate`, the one rulesets require. The job resolves the slots (`lint`, `typecheck`, `test`, `format`, `audit`, `build`), runs them in order, each in a log group with a pass/fail line in the job summary, and fails if any failed (a failed slot doesn't stop the others); one billed minute per run. `preset` (`node`, `python`, `shell`, required) supplies each slot's default; `<slot>_command` overrides it and `none` turns it off. Defaults: node `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check`, `npm audit --audit-level=critical --omit=dev`; python `ruff check .`, `python3 -m unittest discover -s . -p "test_*.py" -v`, `ruff format --check .` (ruff/mypy pinned by `ruff_version`/`mypy_version`, plus `requirements.txt`); shell `shellcheck -S warning` over tracked `*.sh`; `build` has no default. On PRs, nothing runs (and the gate passes) when every changed file matches `paths_ignore` (default `*.md`, `**/*.md`, `.changeset/**`, `docs/**`, `openwiki/**`; empty runs always). Callers name their workflow `Checks` and trigger on `pull_request` and on push to the default branch (the release button needs `ci / gate` on its HEAD). Other inputs: `working_directory`, `node_version` (20), `python_version` (3.12), `apt_packages`, `install_command`, `registry_scope`/`PKG_READ_TOKEN`, `test_reports`, `codecov*`/`CODECOV_TOKEN`, `turbo_team`/`TURBO_TOKEN`; `expect_failure` is for this repo's self-test. No `permissions:`; callers grant `contents: read` |
| `ci-matrix.yml` | Opt-in variant of `ci.yml` with the same inputs: one job and check per slot (`ci / plan`, `ci / lint` … `ci / build`, `ci / gate`), so it bills a minute per job. Use it only when a repo wants each slot as its own check |
| `release-candidate.yml` | `workflow_dispatch` caller (the release button, INF-1983 D46): checks and computes, creates no tag and no GitHub prerelease; the caller's `cd` deploys develop from the output `ref`. Runs only from the default branch, and refuses while `.changeset/pre.json` is in `pre` mode (a repo exiting pre mode may release the coming stable version) or while the latest `ci / gate` on the commit is not green, so the caller's CI must also run on push to the default branch. `X.Y.Z` is `package.json`'s version bumped like `semver.inc` by the highest pending `.changeset/*.md` entry for the package (the next patch when none is pending; from a prerelease, the release it was heading for; single-package repos). Outputs `version` (`X.Y.Z`), `ref` (the SHA to deploy) and `tag` (always empty, kept until v2). `channel` is accepted and ignored. `publish: true` also publishes `X.Y.Z-next.N` under the npm dist-tag `next` with `npm publish --ignore-scripts`, `N` being one more than the highest `X.Y.Z-next.*` in `npm view <name> versions --json` (0 when none or the package is a 404; an existing version makes the publish fail; `install_command` builds without the token; `registry_url`, `scope`; version set in CI only, never committed). `trusted_publishing: true` publishes to npmjs.org through OIDC (caller grants `id-token: write`; npm matches the caller's workflow file, so call it from the same `release.yml` that is the package's trusted publisher); otherwise the job token is used (GitHub Packages, `packages: write`). `dry_run` prints `version`, `ref` and, with `publish`, the npm version it would publish, and changes nothing. Caller grants `contents: read`, `checks: read`; `BOT_APP_ID`/`BOT_PRIVATE_KEY` are accepted but unused |
| `ci-node.yml` | **Deprecated:** use `ci.yml` with `preset: node`; removed in v2. `workflow_call` for npm projects: jobs `lint`, `typecheck`, `test`, `format`, `audit`, `build` and one `gate`. With caller job id `ci` the checks are `ci / lint` and so on, and `ci / gate` is the only CI check a repo requires (failed or cancelled needs fail it, skipped needs pass). Each job runs only when its `run_*` input is true, so a caller that path-filters passes `run_lint: ${{ needs.paths.outputs.code == 'true' }}`. `*_command` inputs override the npm script (default `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check`, `npm audit --audit-level=critical --omit=dev`, `npm run build`). `registry_scope` (e.g. `@cheunjm`) plus the `PKG_READ_TOKEN` secret reads private packages; `test_reports` adds a JUnit upload and test report (caller grants `checks: write`); `codecov` sends coverage to Codecov (`codecov_directory`, `codecov_flags`, `CODECOV_TOKEN` secret; a set directory is also uploaded as the `coverage` artifact); `turbo_team` plus the `TURBO_TOKEN` secret turn on the Turborepo remote cache for the lint, typecheck, test and build steps (a caller's workflow-level `env` does not reach a reusable workflow). `runner` defaults to `ubuntu-latest` and ignores `CI_RUNNER`. The file sets no `permissions:`; callers grant `contents: read` |
| `e2e-maestro.yml` | `workflow_call` for Maestro UI e2e: `platforms` (`android`, `ios`, `web`, comma-separated) fans out to jobs `android`, `ios`, `web` (with caller job id `e2e` the checks are `e2e / android` and so on). The workflow boots the device (an Android emulator, a throwaway iOS simulator that it deletes afterwards, headless Chrome) and passes it to the caller's `test-command` as `E2E_DEVICE` (emulator serial, simulator UDID, web URL) with `E2E_PLATFORM`; an empty `test-command` runs `maestro test <flows-path>` with a JUnit report. The caller supplies `install-command` (default `npm ci`), `setup-command`, `build-command`, `teardown-command` (always runs; use it to stop a local backend on self-hosted runners) and for web `serve-command` plus `web-url`. Maestro is pinned (`maestro-version`, default 2.12.1). `supabase-cli: true` installs the Supabase CLI at `supabase-version` (pinned, default 3.2.0; `latest` hits GitHub API rate limits). Runners (INF-1983 D36): `android-runner` defaults to `mac-studio-android` and `ios-runner` to `mac-studio-ios`, so an app repo registers a `mac-studio-<repo>-android` and a `mac-studio-<repo>-ios` runner and the two platforms run side by side on the Studio; both jobs are skipped for fork PRs. On the Studio both jobs expose only `docker` from `/usr/local/bin`, use an empty `DOCKER_CONFIG`, select Java 17 and need Docker Desktop running for a local Supabase stack; iOS needs Xcode and keeps Maestro away from the host's `~/.android`. The macOS Android job uses the host SDK at `~/Library/Android/sdk` (emulator and `cmdline-tools/latest`), keeps its state in `~/Library/Android/e2e`, and boots an `arm64-v8a` emulator (`android-arch` empty picks the runner's ABI) from a per-runner AVD whose quick-boot snapshot is saved on its first run and reused after; it picks a free emulator port and sets `E2E_DEVICE` and `ANDROID_SERIAL`, so repos share the host. A Linux `android-runner` (e.g. `ubuntu-latest`) keeps the KVM path with `reactivecircus/android-emulator-runner` and a cached AVD. `web-runner` defaults to `ubuntu-latest`. Two jobs of one repo run at once on the Studio, so a caller's local backend must not share ports or Docker names across platforms (arami's `scripts/e2e/env.sh` sets a project id and port block per `E2E_PLATFORM`). The host must keep `~/Library/Android` and `~/Library/Developer/CoreSimulator/Devices` on a disk the runner can read (not an exFAT USB drive): Xcode's build service and CoreSimulator hang or fail there. Concurrency never cancels a running suite: a new push waits for it. Failed jobs upload `artifact-path` (default `.e2e`). On macOS both native jobs take a Studio slot first (`studio-lock`, default `true`, via `.github/actions/studio-lock@v1`, so a caller needs the release that carries it) and release it in an `always()` step after the suite (D37). `app-artifact: <prefix>` installs a same-run build instead of building: artifact `<prefix>-android` holds exactly one `.apk` (`adb install -r`), `<prefix>-ios` exactly one `.tar.gz` or `.tar` with one `.app` directory (`xcrun simctl install`); `setup-command` and `build-command` are skipped, and the install runs after the device boots (on a Linux `android-runner`, inside the emulator script). `include-tags` adds `--include-tags` to the default test command (all three platforms; ignored when `test-command` is set). `environment` runs the android and ios jobs in that GitHub Environment (empty sets none); the optional secret `E2E_TEST_ACCOUNTS` (JSON `{"android":{"email","password"},"ios":{...}}`, usually an Environment secret) is exported per platform as masked `E2E_EMAIL` and `E2E_PASSWORD`, failing with `E2E_TEST_ACCOUNTS has no <platform> entry` when the platform is missing, and nothing is exported when the secret is empty (INF-1983 D45). Spec: `docs/specs/2026-11-22-INF-1908-e2e-maestro/` |

Every callable workflow takes an optional `runner` input that sets `runs-on` (default `ubuntu-latest`). Pass a self-hosted label (e.g. `runner: mac-studio`) to run on the Mac Studio. Self-hosted jobs run on macOS, so only use it on private repos and with steps that don't assume Linux, and register a `mac-studio` runner in the caller repo first, or the jobs queue forever. The three `changeset-*.yml` workflows default `runner` to empty and fall back to the calling repo's `CI_RUNNER` variable, then `ubuntu-latest`, so a repo that sets `CI_RUNNER=mac-studio` runs them on the Studio with no per-caller change, and a repo without the variable stays on hosted runners.

Local to this repo, not callable (no `workflow_call`): `rc-selftest.yml` (dry-runs `release-candidate.yml` on PRs that touch it and checks the outputs are a version, a SHA and an empty tag), `major-tag.yml` (on a stable `vX.Y.Z` tag push, or by dispatch with `tag`, moves the floating `v<MAJOR>` tag to it with `git push` and the arami-bot token; the App needs the Workflows permission, because the tagged commits contain workflow files (D32), so `@v1` callers get the release; the check is `release / major-tag`), `self.yml` (this repo's PR CI, workflow `Checks`: `ci` runs actionlint through `ci.yml`; `node` runs `ci-matrix.yml` and `python`, `shell`, `red`, `docs-only` run `ci.yml` against `fixtures/`; `red` fails a slot on purpose and its gate is inverted, so every gate is green; `studio-lock` acquires two slots, checks they differ, releases both and checks the lock dir is empty).

## Secrets and rulesets

- `secrets.manifest.toml`: every pipeline secret and variable by name, 1Password reference (`op://Openclaw/...`), repos and optional GitHub Environment. It never holds values. App runtime env stays in Doppler (INF-1983, D14).
- `scripts/sync-secrets.py [--dry-run] [--repo R] [--name N]`: reads each reference with `op read` and sets it with `gh secret set` / `gh variable set` over stdin, so values never reach argv or output. It prints one line per name, repo and environment (`ok`, `set`, `missing`, `failed`) and exits 1 on any missing or failed. Tests: `python3 -m unittest scripts/test_sync_secrets.py`.
- `scripts/apply-rulesets.py (--repo R | --all) [--dry-run]`: upserts a ruleset named `default-branch` on the default branch requiring `ci / gate`, `changeset / check` and the repo's `extra_checks` from the manifest, each pinned to the GitHub Actions app (id 15368); repository admins can bypass. It also turns on "Allow auto-merge" for the openwiki merge. `--all` covers repos with `ruleset = true`. Apply it to a repo only after that repo reports `ci / gate`, or every PR there blocks. Private repos need GitHub Pro. Tests: `python3 -m unittest scripts/test_apply_rulesets.py`.
