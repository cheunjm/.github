# .github

Default GitHub templates and reusable workflows for all `cheunjm` repos.

## What belongs here

- Issue templates (bug, feature, chore)
- PR template
- Reusable GitHub Actions workflows (Claude Code, code review, changelog, etc.)
- GitHub-specific configs (FUNDING.yml, CODEOWNERS, etc.)
- Tools registry (TOOLS.md)

## What does NOT belong here

- Coding conventions, standards, or style guides → `cheunjm/conventions`
- Repo-specific workflows or configs → the repo itself
- Secrets, credentials, or environment values → 1Password

## When to update this repo

When working on any `cheunjm` repo and you notice:
- A GitHub workflow being duplicated across repos — extract it here as a reusable workflow
- An issue or PR template improvement that should apply everywhere
- A new GitHub App or tool installed — update TOOLS.md

Ask Jace before adding or changing defaults — these affect all repos.

## Verification

After implementing changes, always run the test/verification steps from the plan before committing or opening a PR. After merging, verify the changes work on the default branch when possible. This includes running workflows locally (e.g. `act`), validating YAML syntax, and testing that calling repos can reference updated workflows. Do not treat verification as optional or skip it.

## Reusable Workflows

Other repos call these via `uses: cheunjm/.github/.github/workflows/{name}.yml@main`. Available:

| Workflow | Trigger |
|----------|---------|
| `db-migration-check.yml` | PR with migration file changes (deterministic SQL risk scan, no LLM) |
| `auto-update-branches.yml` | Push to default branch (merges it into open non-draft same-repo PRs that target it; never rebases) |
| `notify-merge.yml` | Push to default branch (parameterized: `slack_channel`, `repo_label`) |
| `changeset-check.yml` | Pull request (caller workflow is named `Release notes` with job id `changeset`, so GitHub shows `Release notes / changeset / check`): fails unless the PR adds a new `.changeset/*.md` (empty allowed), diffed against the PR's own base so each stack layer needs its own; validates with the pinned changesets CLI; `changeset-release/*` and `dependabot/*` are exempt. Job name is `check`, so the required context is `changeset / check` |
| `changeset-version.yml` | Push to default branch + `workflow_dispatch`: keeps one "Version Packages" PR per repo using the `arami-bot` token; optional `publish`, `install-command`, `registry-url`, `scope` inputs and `PKG_READ_TOKEN` secret. Pins `@changesets/cli` and `changelog-github` and installs them ephemerally (`--no-save`), so repos carry no changesets dependency. Repos that already declare both packages and install them (monorepos, private registries) pass `install-tooling: false` and use their own versions. Runs `changesets/action` v2, which refuses to run on Changesets CLI v2: keep the CLI on 3.x (Node 22+) here and in any repo that declares its own. Its v1 inputs were renamed (`version-script`, `publish-script`, `pr-title`, `commit-message`), and it needs the token via `github-token`. `tag: true` (when `publish` is empty) runs `changeset git-tag` once the Version PR merges, which creates and pushes `vX.Y.Z` and a GitHub release; an existing tag is skipped, so later pushes are no-ops |
| `changeset-prerelease.yml` | `workflow_dispatch` via caller (`phase`: `enter-dev` / `enter-rc` / `release-stable`): opens a PR that enters or exits changesets pre mode instead of pushing to the default branch |
| `ci.yml` | `workflow_call`, stack-agnostic CI in **one job** (INF-1983 D5, D34, D35): with caller job id `ci` the only check is `ci / gate`, the one rulesets require. The job resolves the slots (`lint`, `typecheck`, `test`, `format`, `audit`, `build`), runs them in order, each in a log group with a pass/fail line in the job summary, and fails if any failed (a failed slot doesn't stop the others); one billed minute per run. `preset` (`node`, `python`, `shell`, required) supplies each slot's default; `<slot>_command` overrides it and `none` turns it off. Defaults: node `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check`, `npm audit --audit-level=critical --omit=dev`; python `ruff check .`, `python3 -m unittest discover -s . -p "test_*.py" -v`, `ruff format --check .` (ruff/mypy pinned by `ruff_version`/`mypy_version`, plus `requirements.txt`); shell `shellcheck -S warning` over tracked `*.sh`; `build` has no default. On PRs, nothing runs (and the gate passes) when every changed file matches `paths_ignore` (default `*.md`, `**/*.md`, `.changeset/**`, `docs/**`, `openwiki/**`; empty runs always). Callers name their workflow `Checks` and trigger on `pull_request` and on push to the default branch (the release button needs `ci / gate` on its HEAD). Other inputs: `working_directory`, `node_version` (20), `python_version` (3.12), `apt_packages`, `install_command`, `registry_scope`/`PKG_READ_TOKEN`, `test_reports`, `codecov*`/`CODECOV_TOKEN`, `turbo_team`/`TURBO_TOKEN`; `expect_failure` is for this repo's self-test. No `permissions:`; callers grant `contents: read` |
| `ci-matrix.yml` | Opt-in variant of `ci.yml` with the same inputs: one job and check per slot (`ci / plan`, `ci / lint` … `ci / build`, `ci / gate`), so it bills a minute per job. Use it only when a repo wants each slot as its own check |
| `release-candidate.yml` | `workflow_dispatch` caller (the release button, INF-1983 D26/D27): `channel` `rc` (default) or `next` cuts `vX.Y.Z-<channel>.N` on the caller's commit with the arami-bot token, plus a GitHub prerelease; the tag push deploys develop through the repo's `cd`. Runs only from the default branch, and refuses while `.changeset/pre.json` is in `pre` mode (a repo exiting pre mode may cut rcs of the coming stable version) or while the latest `ci / gate` on the commit is not green, so the caller's CI must also run on push to the default branch. `X.Y.Z` is `package.json`'s version bumped like `semver.inc` by the highest pending `.changeset/*.md` entry for the package (the next patch when none is pending; from a prerelease, the release it was heading for; single-package repos), `N` is the highest existing plus one, from 0, and an existing tag fails the run instead of moving. `publish: true` also publishes `X.Y.Z-<channel>.N` under the npm dist-tag `<channel>` with `npm publish --ignore-scripts` (`install_command` builds without the token; `registry_url`, `scope`; version set in CI only, never committed). `trusted_publishing: true` publishes to npmjs.org through OIDC (caller grants `id-token: write`; npm matches the caller's workflow file, so call it from the same `release.yml` that is the package's trusted publisher); otherwise the job token is used (GitHub Packages, `packages: write`). `dry_run` prints the tag and creates nothing. Caller grants `contents: write`, `checks: read`; secrets `BOT_APP_ID`, `BOT_PRIVATE_KEY`. Outputs `tag`, `version` |
| `ci-node.yml` | **Deprecated:** use `ci.yml` with `preset: node`; removed in v2. `workflow_call` for npm projects: jobs `lint`, `typecheck`, `test`, `format`, `audit`, `build` and one `gate`. With caller job id `ci` the checks are `ci / lint` and so on, and `ci / gate` is the only CI check a repo requires (failed or cancelled needs fail it, skipped needs pass). Each job runs only when its `run_*` input is true, so a caller that path-filters passes `run_lint: ${{ needs.paths.outputs.code == 'true' }}`. `*_command` inputs override the npm script (default `npm run lint`, `npm run typecheck`, `npm run test`, `npm run format:check`, `npm audit --audit-level=critical --omit=dev`, `npm run build`). `registry_scope` (e.g. `@cheunjm`) plus the `PKG_READ_TOKEN` secret reads private packages; `test_reports` adds a JUnit upload and test report (caller grants `checks: write`); `codecov` sends coverage to Codecov (`codecov_directory`, `codecov_flags`, `CODECOV_TOKEN` secret; a set directory is also uploaded as the `coverage` artifact); `turbo_team` plus the `TURBO_TOKEN` secret turn on the Turborepo remote cache for the lint, typecheck, test and build steps (a caller's workflow-level `env` does not reach a reusable workflow). `runner` defaults to `ubuntu-latest` and ignores `CI_RUNNER`. The file sets no `permissions:`; callers grant `contents: read` |
| `e2e-maestro.yml` | `workflow_call` for Maestro UI e2e: `platforms` (`android`, `ios`, `web`, comma-separated) fans out to jobs `android`, `ios`, `web` (with caller job id `e2e` the checks are `e2e / android` and so on). The workflow boots the device (Android emulator with KVM and a cached AVD, a throwaway iOS simulator that it deletes afterwards, headless Chrome) and passes it to the caller's `test-command` as `E2E_DEVICE` (emulator serial, simulator UDID, web URL) with `E2E_PLATFORM`; an empty `test-command` runs `maestro test <flows-path>` with a JUnit report. The caller supplies `install-command` (default `npm ci`), `setup-command`, `build-command`, `teardown-command` (always runs; use it to stop a local backend on self-hosted runners) and for web `serve-command` plus `web-url`. Maestro is pinned (`maestro-version`, default 2.12.1). `supabase-cli: true` installs the Supabase CLI at `supabase-version` (pinned, default 3.2.0; `latest` hits GitHub API rate limits). Runners: `android-runner` and `web-runner` default `ubuntu-latest`, `ios-runner` defaults to `mac-studio` (needs Xcode and, for a local Supabase stack, Docker Desktop running; the job exposes only `docker` from `/usr/local/bin`, uses an empty `DOCKER_CONFIG`, selects Java 17, and keeps Maestro away from the host's `~/.android`) and is skipped for fork PRs. The host must keep `~/Library/Android` and `~/Library/Developer/CoreSimulator/Devices` on a disk the runner can read (not an exFAT USB drive): Xcode's build service and CoreSimulator hang or fail there. Concurrency never cancels a running suite: a new push waits for it. Failed jobs upload `artifact-path` (default `.e2e`). Spec: `docs/specs/2026-11-22-INF-1908-e2e-maestro/` |
| `openwiki-update.yml` | `workflow_call` on push to the default branch: generates or updates the repo's OpenWiki through the Studio's LiteLLM (default `base_url` `http://127.0.0.1:4001/v1`, `model_id` `gpt-6.1-sol`, Responses API; the ChatGPT subscription, no API key), opens a docs PR and squash-merges it when only `openwiki/` changed and a secret scan is clean. `generate` runs on `runner`, default `mac-studio-openwiki` (INF-1983 D28): every repo has a Studio runner with that label that does no mobile work; the repo variable `OPENWIKI_RUNNER` still overrides it until v2. `publish`, which holds the write token, runs on `ubuntu-latest` unless `publish_runner` is set. Needs `LITELLM_API_KEY`. The wiki PR is opened with the arami-bot App (`use_app`, default true; `BOT_APP_ID`/`BOT_PRIVATE_KEY`) and carries an empty changeset (`changeset`, default true), so it runs the checks rulesets require; repos with a ruleset need "Allow auto-merge", which `apply-rulesets.py` turns on. The squash merge keeps `[skip ci]` until INF-1983 stage 4. Callers skip docs-only and `.changeset`-only pushes with `paths-ignore` |
| `auto-label.yml` | Pull request opened (adds the `decision-log` label to `feat/` and `fix/` branches; the calling job must grant `pull-requests: write`; this repo calls it from `labels.yml`) |
| `decision-dispatch.yml` | `workflow_call` on a merged PR (caller trigger `pull_request: closed`): when the PR has the `decision-log` label, sends a `new-decision` dispatch to `cheunjm/engineering-log` with the GitHub App token (needs `BOT_APP_ID` and `BOT_PRIVATE_KEY`; callers use `secrets: inherit` and `permissions: {}`). With caller job id `decisions` the check is `decisions / dispatch`. PR fields reach the script only through `env:` and the payload is built with `jq --arg`, so a title or body cannot inject shell. Optional `runner` input |

Every callable workflow takes an optional `runner` input that sets `runs-on` (default `ubuntu-latest`). Pass a self-hosted label (e.g. `runner: mac-studio`) to run on the Mac Studio. Self-hosted jobs run on macOS, so only use it on private repos and with steps that don't assume Linux, and register a `mac-studio` runner in the caller repo first, or the jobs queue forever. The three `changeset-*.yml` workflows default `runner` to empty and fall back to the calling repo's `CI_RUNNER` variable, then `ubuntu-latest`, so a repo that sets `CI_RUNNER=mac-studio` runs them on the Studio with no per-caller change, and a repo without the variable stays on hosted runners.

Local to this repo, not callable (no `workflow_call`): `rc-selftest.yml` (dry-runs `release-candidate.yml` for both channels on PRs that touch it), `major-tag.yml` (on a stable `vX.Y.Z` tag push, or by dispatch with `tag`, moves the floating `v<MAJOR>` tag to it with `git push` and the arami-bot token; the App needs the Workflows permission, because the tagged commits contain workflow files (D32), so `@v1` callers get the release; the check is `release / major-tag`), `self.yml` (this repo's PR CI, workflow `Checks`: `ci` runs actionlint through `ci.yml`; `node` runs `ci-matrix.yml` and `python`, `shell`, `red`, `docs-only` run `ci.yml` against `fixtures/`; `red` fails a slot on purpose and its gate is inverted, so every gate is green).

## Secrets and rulesets

- `secrets.manifest.toml`: every pipeline secret and variable by name, 1Password reference (`op://Openclaw/...`), repos and optional GitHub Environment. It never holds values. App runtime env stays in Doppler (INF-1983, D14).
- `scripts/sync-secrets.py [--dry-run] [--repo R] [--name N]`: reads each reference with `op read` and sets it with `gh secret set` / `gh variable set` over stdin, so values never reach argv or output. It prints one line per name, repo and environment (`ok`, `set`, `missing`, `failed`) and exits 1 on any missing or failed. Tests: `python3 -m unittest scripts/test_sync_secrets.py`.
- `scripts/apply-rulesets.py (--repo R | --all) [--dry-run]`: upserts a ruleset named `default-branch` on the default branch requiring `ci / gate`, `changeset / check` and the repo's `extra_checks` from the manifest, each pinned to the GitHub Actions app (id 15368); repository admins can bypass. It also turns on "Allow auto-merge" for the openwiki merge. `--all` covers repos with `ruleset = true`. Apply it to a repo only after that repo reports `ci / gate`, or every PR there blocks. Private repos need GitHub Pro. Tests: `python3 -m unittest scripts/test_apply_rulesets.py`.
